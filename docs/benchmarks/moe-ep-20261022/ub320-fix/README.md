# `-ub 320` の落ちる問題の修正と、pp をさらに伸ばす試み

TB250、2026-10-22。LFM2.5-8B-A1B Q4_0、llama.cpp `23b0202`、SGL `feat/moe-expert-parallel`。作業場所 `~/moe-ep/fix/`（ビルドは `build/`（CL11）と `build-cuda/`（`-DCL11_WITH_CUDA=ON`））。測定は `~/moe-ep/sglx/run.sh` 方式の flock + 温度待ちで 1 本ずつ、速度は `perf pin`（`scripts/sess.sh`、終了時に `perf auto`、`trap EXIT`）。数値は `logs/` の実測。**【推定】** と書いたものだけが実測でない。

## 結論

1. **原因は `pdev_ggml` のグラフキャッシュのぶら下がりポインタ**。`ggml_gallocr_reserve` が、より大きな N のグラフを作るときに計算バッファを解放して作り直す。ところが、前に作った別の N のグラフ（キャッシュ、最大 4 個）のテンソルは、解放済みの `ggml_backend_buffer` を指したままだった。`ggml_gallocr_alloc_graph` は、データ位置（Vulkan のバッファは基点が同じ 0x1000）が変わらないので気づかず、`ggml_backend_tensor_set_async` が死んだバッファの `buft` を読み、ggml-vulkan の `unsupported buffer type` で落ちる。`-ub` 192 / 256 / 512 で落ちなかったのは、解放済みの領域が偶然新しいバッファ構造体に再利用されていたため（N = 1 のグラフ、つまりトークン生成も同じ形でぶら下がっていた）。修正は **大きい N で reserve し直すとき、キャッシュ済みの他のグラフを全部捨てる**（`adapters/ggml/composite/pdev_ggml.cpp`、コミット `ffa4c49`、`llama.cpp` は無改造）。
   - 確認: 診断ビルドで `x->buffer->buft` を実行時に比較し、`-ub 320` で `DBG Vulkan0 N=64 ... MISMATCH ... reserved=192 graphs=3` を捕捉（`logs/d1_C320.log`）。修正後は同じコマンドが最後まで走る。
2. 正しさ（§8.1、`-b 512 -ub 320`）: **KLD（CPU 基準）0.020757、top-1 93.92 %**（基準 ≤ 0.0259 / ≥ 91.94 % を満たす）。自己整合（SGLX 1 枚 vs C）**KLD 0.000002、top-1 99.90 %**（基準 < 0.001）。`test-backend-ops -b SGLX0 -o MUL_MAT,GET_ROWS`: tb250 656/658（失敗 2 件は既知の Vulkan0 の NaN）、Mac 658/658。
3. 速度の劣化なし: `perf pin`、REPS=10、`-ub 320`、交互 2 回で、修正後と修正前のプラグインは pp / tg / pg が同等（下の表）。
4. **pp をさらに伸ばす試みは、今回は成果なし**。RX の VRAM を空けて 22 層目を RX に載せる案は、(a) 実測で必要量が想定より大きい（`-ub 320` でも 22 層 + SGLX の RX 分は 4064 MiB に収まらない）、(b) 収まるように RX の SGLX 分を 0 にしテンソルを一部 WX へ戻した構成でも pp は +0 %（709〜710 vs 714）、(c) そもそも 2 ubatch が重なる pp では、VRAM に収まる `-ub` での見込みが +17 % ではなく +2〜6 %（下のモデル、**【推定】**）。tg / pg は run 間のドリフトが大きく、この構成の tg は比較できていない。
5. **`-ub 320` の突出は、タイルの端数ではなく、2 ubatch の RX 区間と WX 区間が重なる釣り合いの点**と考えるのが測定に合う（MUL_MAT_ID の時間は n に対して滑らかで、320 に凹みも段もない）。`-ub 320` は pp512 向けの値で、pp1024 では 384、pp256 では分割しない方がよい（下）。
6. CUDA pdev 版（`GGML_SGLX_SPLIT=...,CUDA0:0.2,CUDA1:0.1`）の `-ub 320` は CL11 版と同等（pp 706.6 / 699.0 vs 705.7 / 705.1）。

## 1. 修正の詳細

`pdev_ggml::graph_for` は N ごとの MUL_MAT グラフ（`x` → `y = W·x`）を 1 つの `ggml_gallocr` で順に割り当てる。N が `reserved_N` を超えるときだけ `ggml_gallocr_reserve` を呼ぶ。この呼び出しで ggml-alloc は古いバッファを解放し、新しい大きなバッファを作る。キャッシュには前の N のグラフが残り、そのテンソル（`x`, `y`）の `buffer` は解放済みのまま。次にそのグラフを使うとき、`ggml_gallocr_alloc_graph` は node の割り当てが前回の計画と同じなら何もしない。Vulkan のバッファは `get_base` が固定（0x1000）のため `data` も一致して、`x->buffer` の更新が行われない。

perplexity の `-b 512 -ub 320` は N = 64（起動時の小さなバッチ）→ 192 → 320 のように大きくなる順で呼ぶため、必ず起きる。`-ub 192 / 256 / 512` では、解放された `ggml_backend_buffer` の領域が次の `new` で同じ型の構造体として再利用され、`buft` が一致して見かけ上は通っていた。

修正前: 診断ログ（`SGLX_DBG`、コミットしていない）で `buf=... buft=0x5604933a86f0 want=0x56048e50d8a0 MISMATCH`（`logs/d1_C320.log`）。

## 4. pp をさらに伸ばす

### 4.1 `-ub` ごとの 1 ubatch の時間（C1、`-ts 5/1`、`-p n -ub n`、REPS=3、`logs/fA_*`）

| n | 64 | 96 | 128 | 160 | 192 | 224 | 256 | 288 | 320 | 352 | 384 | 448 | 512 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| t/s | 237 | 306 | 377 | 414 | 475 | 494 | 532 | 544 | 576 | 586 | 618 | 641 | 672 |
| 1 ubatch の時間 ms | 271 | 314 | 339 | 386 | 405 | 454 | 481 | 529 | 556 | 601 | 621 | 699 | 762 |

時間は n にほぼ直線（約 215 ms + 1.07 ms × n）で、**320 に凹みも段もない**。MUL_MAT_ID の時間（同期ロガーの版、`logs/fB_prof_n*`）も滑らか: RX 175 / 193 / 213 / 233 / 275 ms（n = 192 / 256 / 320 / 384 / 512）、WX 112 / 140 / 175 / 182 / 218 ms。n あたりでは RX 0.91 → 0.54 ms、WX 0.58 → 0.43 ms と単調に下がるだけで、320 だけ効率が高いという形ではない。ggml-vulkan は AMD で MUL_MAT_ID に S / M タイルだけを持ち（`mul_mat_id_l = false`）、n > 32 なら一律 M タイル（選択器 `m <= 32 || n <= 32 → S`、`n <= 64 → M`、それ以外は最後=M）。つまりタイルの選択は 320 と 512 で同じ。

### 4.2 320 が突出する理由（モデル、**【推定】**）

実測の pp512 は 2 ubatch（320 + 192）で 726 ms。1 ubatch ずつの時間の和は 556 + 405 = 961 ms で、**235 ms ぶん重なっている**。RX（21 層）の区間と WX（3 層）の区間が、ubatch をまたいで並ぶためと考えられる（ggml-vulkan の非同期投入）。区間を `T(n) = R(n) + W(n)`、`R = ρT`、重なりを `T = R(a) + max(W(a), R(b)) + W(b)`（a、b は 1 つ目と 2 つ目の ubatch）としたモデルで、ρ = 0.55〜0.6 のとき、前回の `-ub` 掃引（192〜512 の 12 点）に **RMSE 17 t/s で合う**（320 付近が山、512 単独 672、192〜224 が谷。計算は `scripts/model.py`）。山の尖り（304 → 694、320 → 717、336 → 693）まではモデルで再現できず、**モデルは定性的な説明**にとどまる。RX と WX が、ubatch 同士で互いの待ちを隠せる点が 320 + 192 にあるという読みで、タイルの端数ではない。

他の長さでの実測（SGLX C、REPS=3、`logs/f7_*`）:

| プロンプト | 分割ごとの t/s |
| --- | --- |
| pp256（`-b 256`） | `-ub` 96: 415、128: 485、160: 489、192: 507、**256（分割なし）: 538**。C1: 256 → 529、128 → 479 |
| pp1024（`-b 1024`） | `-ub` 256: 784、320: 796、**384: 851**、448: 826、512: 837。C1: 320 → 792、512 → 825 |

`-ub 320` が良いのは **pp512 だけ**（pp1024 では 384、pp256 では分割しない方がよい）。同等の効率は、プロンプト長に合わせて `-ub` を選ぶことで出せる（pp1024 の 384 が C1 の最良 825 を +3 % 上回る）。`-ub` を固定するなら、プロンプトの長さの分布に合わせる必要がある。

### 4.3 RX の VRAM（実測）

RX 6400: 総量 4080 MiB、起動時の他使用 16 MiB、使えるのは 4064 MiB（`mem_info_vram_total/used`、`scripts/peak.py` で 0.1 秒間隔のピーク）。

| 構成（`-ub 320`） | RX の VRAM ピーク | pp512 / tg128 / pg |
| --- | --- | --- |
| C1 `-ts 5/1` | 3921 MiB | 711.0 / 52.6 / 200.1 |
| SGLX C `-ts 5/1/0` | 3993 MiB（**SGLX の RX 分で +72 MiB**） | 714.5 / 66.6 / 236.6（`fD_ref_ts51`） |
| C1 `-ts 6/1` | 4061 MiB（GTT +79 MiB） | **139.1** / 54.7 / 93.9 |
| SGLX C `-ts 6/1/0` | 4051 MiB | **138.4** / 13.4 / 45.5 |
| 同、RX の SGLX 分を 0.25（約 36 MiB） | - | **139.4** / 23.0 / 63.9 |
| 同、RX の SGLX 分を 0（`Vulkan1:0.5,CL11_0:0.3,CL11_1:0.2`） | 4050 MiB | **140.5** / 60.0 / 97.0 |

22 層目を RX に載せる `-ts 6/1` は、`-ub 320` でも、RX の SGLX 分を 0 にしても pp が約 140 に落ちる（VRAM がほぼ満杯で、実行時の確保が溢れるため）。内訳（`GGML_VK_MEMORY_LOGGER`、`logs/fC_c1_ts61.log`）: モデル 4010.7 + KV 6.0 + RS 0.25 + **計算バッファ 76.3（`-ub 320`）** = 約 4093 MiB に、実行時の prealloc が数 MiB 載る。使える 4064 MiB に対して約 33 MiB 足りず、SGLX の RX 分（72 MiB）があるとさらに足りない。前回の「約 90 MiB 不足」は `-ub 512` での見積もり（計算バッファ 122 MiB）の値で、`-ub 320` では約 33 MiB（C1）、SGLX C では約 105 MiB。

### 4.4 RX から外す・WX に戻す試み（`scripts/fq5.sh`、`logs/fD_*`）

`-ts 6/1/0` にして 22 層目（blk.21）の **`ffn_down_exps`（63 MiB）だけ `-ot` で WX に戻す**構成（RX は 22 層目の attention とゲート / アップを持ち、WX は down だけを計算。境界の数は 5/1 と同じ、swiglu の活性（1792 × 4 × N）が RX → WX に渡る）。RX の SGLX 分は 0（S0）か 0.1（S1）に減らす。

| 構成（`-ub 320`、REPS=3） | RX ピーク | pp512 | tg128 | pg |
| --- | --- | --- | --- | --- |
| 5/1 SGLX C（基準、セッション先頭） | 3993 | 714.5 ± 5.7 | 66.6 | 236.6 |
| 6/1 + down→WX、RX 分 0（S0） | 4023 | 709.5 ± 8.1 | 58.4 | 217.1 |
| 6/1 + down→WX、RX 分 0.1（S1） | 4044 | 709.9 ± 8.1 | 51.9 | 197.6 |
| 6/1 + up, down→WX、RX 分 0.5（C） | 4059（GTT も 3910 に増加） | 680.6 ± 9.8 | 60.3 | 214.2 |
| 6/1 + down→WX、RX 分 0、`-ub 256` | 4015 | 699.6 ± 4.0 | 50.1 | 191.6 |

- **pp は基準と同じか下**（-0.7 〜 -5 %）。RX の VRAM を空ける目的は、この構成では達成できていない（収まっても pp が伸びない）。
- tg / pg の低下は、この実行がセッション中盤にあり、**ドリフトの影響を分離できていない**（同じセッションで基準を最後にもう一度測っていない。別セッション `f6_*` では SGLX C が先頭 66.2 → 末尾 62.2 と動いた）。したがってこの表の tg / pg は、基準との差を結論にしない。pp は ±1 % で安定している（C1 の run 間差も 1.1 %）。
- 22 層目の全部（198 MiB）は載らない。載るのは 63 MiB 単位のテンソル 1〜2 個まで（`-ub 320`、RX 分 0 のとき）。

### 4.5 なぜ伸びないか（モデル、**【推定】**）

4.2 のモデルで、1 層を WX → RX に移す（R × 22/21、W × 2/3）とすると、`-ub 320` で 701 → 743 t/s、`-ub 384` で 667 → 763（それぞれ約 +6 %、+14 %）になる計算。ただし RX の計算バッファが `-ub 384` で約 91 MiB 必要になり、VRAM の制約で `-ub` を上げられない。`-ub 256` では 678 → 718（+6 %）で、基準の 701（`-ub 320`）に対して +2 %。前回の README の「+17 % 前後」は 1 ubatch の傾き（`-ts` 4/1 → 5/1 → 6/1 の pp）からの見積もりで、2 ubatch が重なる pp512 には当てはまらない。実測の 4.4 は、モデルが予測した +6 % にも届いていない（RX → WX の活性の受け渡し 9 MiB / ubatch などの追加費用が上回ると考えられるが、未検証）。

## 6. 残課題

- pp512 の RX 22 層化は、RX の VRAM が計算バッファ分も含めて 4064 MiB に収まらず、収めると pp が伸びない。伸ばすなら、(1) ggml-vulkan の MUL_MAT_ID の計算バッファを小さくする（llama.cpp 側の改造が要る）、(2) pp のあいだだけ RX の SGLX 分を NVIDIA 側に退避する、(3) RX に載せる 1 層を 63 MiB 単位のテンソル数と `-ub` の組で全探索する、のいずれか。
- 4.4 の tg / pg は同一セッション内の基準との比較ができていない。やり直すなら基準を前後で測る。
- 4.2 のモデルの検証は、shim の時間軸（`scripts/tl.py`）で `-ub 320` と 256 の 1 pass の RX / WX の重なりを直接見る方法がある。未実施。
- `-ub` の自動選択（プロンプト長から分割を決める）は未実装。pp512 は 320、pp1024 は 384、pp256 は分割しない。
