# C1（RX 6400 + WX 2100 公式 Vulkan 層分割）の tg 頭打ち原因の実測

測定日 2026-10-21、tb250、llama.cpp `23b0202a1`（ベースラインと同じビルド）。llama.cpp / SGL 本体のコードは変更していない。測定用のものだけ自作した（後述の「自作ツール」）。すべて実測で、推定は「推定」と明記した。C1 のコマンドは baseline README と同じ: `llama-bench -dev Vulkan0/Vulkan1 -ngl 99 -ts 5/1 -sm layer -b 512 -ub 512 -t 2`。

## 結論

**C1 の tg は「ホスト CPU 律速」でも「固定オーバーヘッド律速」でもなく、GPU 2 枚の実行時間が直列に足される構造で、各 GPU がほぼメモリ帯域で埋まっている。** 22.7 ms/token のうち約 21.8 ms（96 %）が 2 枚の GPU の実行時間、ホスト側の隙間は約 0.8 ms。

1. トークンの流れは「RX 6400 が 21 層（約 10.9 ms）→ 隙間 0.4 ms → WX 2100 が 3 層 + 出力射影（約 10.9 ms）→ 隙間 0.4 ms」の直列。RX と WX は同時には動かない（層分割は 1 トークンの中で並列にならない）。
2. WX の 10.9 ms のうち約 5.6 ms は **出力射影（q6_K、m=128000、215 MB）1 回**。出力層は層分割の仕様で常に最後のデバイス（WX 2100）に置かれる。同じ演算が RX では 1.7〜2.5 ms。
3. tg が `-ts` 5/1〜13/3 と `-ub` 64〜1024 で一定なのは、**`-ts` 5/1・9/2・13/3 がどれも同じ層割り当て（RX 21 層 / WX 3 層）になるため**（llama.cpp の割り当て式で確認）。`-ub` は tg のグラフに影響しない。層割り当てが変わる `-ts`（2/1〜4/1）では tg は 36〜42 t/s と下がり、6/1（RX 22 層）は RX の VRAM（4 GiB）が溢れて 38.6 t/s に落ちる。つまり **5/1 は RX の VRAM 容量で決まった上限**で、tg の頭打ちは層分割 + RX の VRAM 容量 + WX の帯域の組み合わせ。
4. ホスト CPU は 1 トークンあたり 11.8〜12.1 ms 使っているが、その約 73 %（約 8.7 ms）は GPU 完了待ちのスピン（`ggml_vk_wait_for_fence` の `getFenceStatus` ループ）で、実作業は約 3.3 ms。この 3.3 ms は GPU 実行と重なっていて隠れている。`-t 1` と `-t 2` は同一（GPU のみのグラフでは CPU ワーカースレッドが使われない）。
5. 設定だけで効くものは小さい（FORCE_MMVQ +2 %、出力を RX へ置く `-ot` は tg +6〜9 % だが RX の VRAM が満杯になり pp が 1/4 に落ちる）。抜本策は「層分割をやめて 2 枚を同時に動かす」（今回のプロジェクトの expert 並列）で、実測した 1 境界あたり約 0.4 ms の同期コストが層ごとに乗ると効果が消えるため、同期を層ごとにしない設計が必要（推定、下記）。

## 1 トークン 22.7 ms の内訳（C1、`-ts 5/1`、tg、直列）

トークン周期は `vkQueueSubmit` / `vkGetFenceStatus`（成功時刻）を LD_PRELOAD の計測 shim で打刻して得た（`logs/tl_g_fw_5_1.*`、安定した 73 トークンの平均。shim 有りで tg 43.94 t/s、周期 22.63 ms。shim 無しの tg は 44.1 t/s なので誤差は 1 % 未満）。

| 区間 | ms/token | 割合 | 根拠 | 備考 |
| --- | --- | --- | --- | --- |
| GPU RX 6400（21 層、MoE 19 + dense 2） | 10.92 | 48.3 % | 最初の RX submit から RX フェンス成功まで（実測） | 内訳は下の perf logger 表 |
| 境界（RX→WX、ホスト経由の隠れ状態 8 KiB の転送 submit + 待ち） | 0.38 | 1.7 % | 実測 | PCIe 転送量ではなく submit / フェンスの遅延 |
| GPU WX 2100（3 層 + 出力射影） | 10.90 | 48.2 % | 最初の WX submit から WX フェンス成功まで（実測） | うち出力射影 q6_K が約 5.6 ms（perf logger） |
| ホストその他（WX 完了 → ロジット取得 → 次トークンの最初の submit） | 0.43 | 1.9 % | 実測 | 次トークンのグラフは再利用（再構築なし） |
| 合計（周期） | 22.63 | 100 % | 実測 | |

補足: ホスト CPU は上の区間と並行して動く。トークンあたり CPU 時間は 11.8〜12.1 ms（user 11.0〜11.4 + sys 0.7〜0.8）で、内訳は後述の「1. ホスト CPU」。ホストの実作業 約 3.3 ms は GPU 実行中に重なるので周期には現れない。

### GPU 内訳（`GGML_VK_PERF_LOGGER`、2 デバイス用に自作パッチ版で取得）

2 デバイスで assert する `GGML_VK_PERF_LOGGER`（`ggml-vulkan.cpp` の `GGML_ASSERT(ctx->compute_ctx.expired())`）を、**別ディレクトリに作った 1 行パッチ版 `libggml-vulkan.so`** で回避して取得した（`logs/pl_c1.*`、23 トークンの平均）。ロガー有効時は演算ごとに同期するため合計が実際より 10 % 程度大きい（RX 12.0 ms vs 実測 10.9 ms、WX 9.4 ms vs 実測 10.9 ms）。

| デバイス | 区分 | ms |
| --- | --- | --- |
| RX 6400（21 層） | MUL_MAT_ID（expert up/gate/down） | 6.76 |
| | mat-vec（q4_0 の conv / attn / dense、f16、f32） | 3.65 |
| | その他の小さな演算（norm、add、mul、glu、copy、ssm_conv 等） | 1.61 |
| | 合計 | 12.01 |
| WX 2100（3 層 + 出力） | 出力射影 q6_K mat-vec（m=128000、k=2048） | 5.59 |
| | MUL_MAT_ID | 2.38 |
| | mat-vec | 0.87 |
| | その他 | 0.56 |
| | 合計 | 9.40 |

- RX の MUL_MAT_ID（19 層、1 層あたり up/gate 2 回 + down 1 回）は 1 層 約 0.35 ms。1 層で読む expert は 4 expert × 3 行列 × 2048 × 1792 × 18/32 B ≈ 24.8 MB（推定）なので実効約 70 GB/s。dense の mat-vec は同じ RX で約 116 GB/s（下の回帰）出ているので、MoE 用カーネルは dense より帯域効率が低い（推定）。
- 出力射影の GPU 時間: WX 5.6 ms（≒ 38 GB/s）、RX 1.7〜2.5 ms（逆順構成 `pl_rv_1_5` で 1.97 ms、`-ot` 構成で 2.48 ms）。
- WX 単独（`-ncmoe 24`、experts は CPU）の出力射影は 11.7 ms と出たが、これは WX が experts 待ちでほぼ遊んでいてクロックが下がっていた run の値（`logs/pl_dev1_ncmoe24.*`）。C1 のように継続して使われる状況では 5.6 ms。

## 1. トークンあたりのホスト CPU（item 1）

`/usr/bin/time` が tb250 に無いので `wait4` の rusage と `/proc/<pid>/task/*/schedstat` のサンプリング（`scripts/sampler.py`、0.1 s 間隔）で測った。tg のみの定常区間（モデルロード後、約 440 トークン）の値。

| 条件 | tg128〜512 (t/s) | CPU 時間/token | user | sys | CPU 使用率（メインスレッド） |
| --- | --- | --- | --- | --- | --- |
| `-t 2` | 44.33（n=512） | 11.84 ms | 11.05 ms | 0.80 ms | 約 52 % |
| `-t 1` | 43.66（n=512） | 12.10 ms | 11.42 ms | 0.69 ms | 約 53 % |

- スレッド別: CPU を使うのは **メインスレッド 1 本だけ**。他の 4 本（`llama-b:disk$0`、Mesa のシェーダキャッシュ用）は 0 ms。`-t` は tg に影響しない（GPU のみのグラフには CPU 側の計算がなく、ggml のワーカースレッドプールが使われない）。`--poll 0` も tg 44.22（基準 44.08、差なし）。
- モデルロード・ウォームアップ区間（開始〜約 6 s）はメインスレッドが 100 % だが、tg 中は約 52 %（残りは待機）。

### ホスト CPU の中身（CPU 時間サンプリング、perf の代替）

tb250 は `perf_event_paranoid=3`、`perf` / `gdb` / `strace` も無い（sudo 不可）。代わりに **LD_PRELOAD の SIGPROF サンプラ**（`scripts/sprof.c`、`ITIMER_PROF` + `backtrace()`、シンボル解決は `nm`）を作った。カーネル HZ=250 のためサンプル間隔は実効 4 ms（2719 サンプル ≒ 10.2 s で一致）。`llama_context::decode` を含むスタックだけ集計（`logs/sprof_c1.txt.gz`、1204 サンプル ≒ トークンあたり 11.9 ms）。

| 区分 | サンプル割合 | ms/token（推定、割合 × 11.9） |
| --- | --- | --- |
| `ggml_vk_wait_for_fence` 自身（GPU 完了待ちのスピンループ） | 73.2 % | 約 8.7 |
| 実作業（残り） | 26.8 % | 約 3.2 |
| └ `ggml_vk_build_graph`（ノード走査、融合判定、ディスパッチ記録） | 実作業の 39 % | 約 1.3 |
| └ `ioctl`（DRM の submit） | 実作業の 28 % | 約 0.9 |
| └ `ggml_vk_submit`（radv の submit 本体、上の ioctl を含む） | 実作業の 21 % | 約 0.7 |
| └ llama のグラフ構築 / 入力設定 | ほぼ 0（`LLAMA_GRAPH_REUSE_DISABLE=1` にすると tg が 44.17→38.31 に落ちるので、再利用が効いている） | |

`vkCmdDispatch` 等の Vulkan API 呼び出し自体は 1 トークンあたり合計約 1.3 ms（shim 実測）で、1 トークンのディスパッチ数は約 530。ホストの実作業は GPU 実行（RX 10.9 ms）の裏で終わり、GPU の方が遅い。

## 2. GPU 稼働率（item 2）

`gpu_busy_percent` を 10 ms 間隔で 840 サンプル（`logs/gpu_c1.json`、tg 約 8 s 分）。

| デバイス | busy 平均 | 備考 |
| --- | --- | --- |
| RX 6400（card1） | 47.5 % | 値は平滑化されていて 27〜72 の連続値 |
| WX 2100（card5） | 43.0 % | 0 と 100 の二値（0: 387、100: 296 サンプル）。瞬時値 |

トークン周期に占める各 GPU の実行区間（RX 48 %、WX 48 %）と整合する。**2 枚が交互に動いていて、どちらも自分の区間は埋まっている**。クロック（50 ms 間隔で取得）: RX 6400 は sclk 状態 1（上限 2320 MHz に対し 1565〜1695 MHz）、mclk は最大状態（1000 MHz）、WX 2100 は sclk 最大（1219 MHz）、mclk 最大（1500 MHz）。

## 3. 層数と ms/token の関係、固定オーバーヘッド（item 3）

### 3a. C1 内で層割り当てを変える（`-ts`、順方向 Vulkan0/Vulkan1）

層割り当ては llama.cpp の式（出力層を含む 25 スロットを累積 `-ts` で分ける）で計算し、出力層は常に最後のデバイス。区間は shim 実測（73 トークン平均、`scripts/an_phase2.py 2`）。

| `-ts` | RX 層 | WX 層（+出力） | tg (t/s) | 周期 (ms) | RX 区間 (ms) | 境界 (ms) | WX 区間 (ms) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2/1 | 17 | 7 | 36.41 | 27.39 | 10.32 | 0.93 | 15.53 |
| 3/1 | 19 | 5 | 39.94 | 24.97 | 10.46 | 0.76 | 13.24 |
| 4/1 | 20 | 4 | 42.52 | 23.40 | 10.26 | 0.54 | 12.10 |
| **5/1（C1）** | 21 | 3 | **43.94** | 22.63 | 10.92 | 0.38 | 10.90 |
| 6/1 | 22 | 2 | 38.59 | 25.87 | 14.23 | 0.70 | 10.44 |

- WX 区間 = 約 7.4 ms + 約 1.16 ms/層（最小二乗の目安。7.4 ms は出力射影 約 5.6 ms + 固定分。推定）。層を WX から RX へ 1 層動かすたびに約 1.2 ms 減る。
- RX 区間は 17〜21 層で 10.3〜10.9 ms とほぼ平坦（約 0.15 ms/層）。perf logger の演算合計から期待する約 0.55 ms/層より小さく、**理由は未特定**（RX が WX 区間の約 11 ms 遊んだ後に毎トークン立ち上がる影響など、GPU 電源 / クロック側の仮説はあるが未検証）。
- 6/1 は RX が 22 層で VRAM（4 GiB）を超え、RX 区間が 14.2 ms に悪化。VRAM 使用量（`mem_info_vram_used`）は 5/1 で RX 3953 MiB / 4080 MiB、WX 1086 MiB / 2048 MiB。**RX の VRAM 容量が層割り当ての上限を決めている**。
- `-ts 5/1`、`9/2`、`13/3` は全部 21/3 に割り当てられる（baseline の頭打ちはこれ）。

### 3b. 小さな dense モデルの単体 Vulkan（全層が GPU に載る）

同じ系列の LFM2.5 dense（230M / 350M / 1.2B、Q4_0 / Q8_0、全 16 層）を RX 単体・WX 単体で tg 計測（`-n 256 -r 3`、`logs/dense_*`、`scripts/an_dense.py`）。ms/token をモデルサイズで直線回帰した。

| デバイス | ms/token = 固定 + 傾き × サイズ | 傾きから見た実効帯域 |
| --- | --- | --- |
| RX 6400 | 1.14 ms + 8.61 ms/GB（Q4_0 のみ 1.00 + 9.29、Q8_0 のみ 1.07 + 8.55） | 約 116 GB/s |
| WX 2100 | 3.80 ms + 24.28 ms/GB（Q4_0 のみ 3.41 + 26.32、Q8_0 のみ 3.57 + 24.13） | 約 41 GB/s |

dense モデルの 1 トークンあたりのディスパッチは約 240 で、固定分はディスパッチ遅延と submit / フェンスの分。**固定オーバーヘッドは RX 約 1.1 ms、WX 約 3.8 ms（この回帰の値）**。C1 ではこれに境界 2 回の約 0.8 ms が加わるので、重みの帯域に比例しない分は **約 5〜6 ms/token（約 25 %、推定）**。残りの約 17 ms が帯域比例分。

## 4. perf の可否と代替（item 4）

- `perf_event_paranoid=3`、`perf`・`gdb`・`strace`・`valgrind`・`/usr/bin/time` は tb250 に無く sudo も不可 → perf は使えない。
- 代替: 上記の SIGPROF サンプラ（ホストのホットスポット）、Vulkan shim（API 呼び出し時間とトークンのタイムライン）、2 デバイス用に 1 行パッチした `libggml-vulkan.so`（別ディレクトリ `~/moe-ep/c1p/bin-patched/`）による `GGML_VK_PERF_LOGGER`。ホストの CPU ホットスポットの結論は「実作業は `ggml_vk_build_graph` と DRM ioctl が中心で、radv のドライバ内部 + libdrm 自身では約 0.7〜0.9 ms」。

### 出力射影を RX に置く（`-ot "token_embd\.weight=Vulkan0"`）

LFM2.5 は入力埋め込みと出力が同一テンソル（`TENSOR_DUPLICATED`）で、`-ot` で `token_embd.weight` を `Vulkan0` に指定すると入力側と出力側が同じ 215 MB を共有する（ローダのコードで、複製は同じ buffer type なら再利用）。

| 構成 | tg (t/s) | pp512 (t/s) | 備考 |
| --- | --- | --- | --- |
| 基準 `-ts 5/1 -ub 512` | 44.08 ± 0.13（`-r 5`） | 644.7 ± 2.9 | |
| `-ot` + `-ts 5/1`、tg のみ `-r 3` | 47.93 ± 0.66 | | **+8.5 %** |
| `-ot` + `-ts 5/1`、pp512 付き `-r 5` | 44.38 ± 5.21（47.9, 46.2, 47.6, 44.9, 35.3） | 162.3 | tg が反復ごとに不安定、pp が 1/4 |
| 同、`-ub 128` | 47.07（44.6 が 1 回） | 138.8（基準 `-ub 128` は 364.5） | |
| 同、`-ub 256` / `-ub 64` | 45.15（37.4 が 1 回）/ 37.08 | 152.1 / 115.8 | |
| `-ot` + `-ts 4/1` | 31.57 | 161.3 | 悪化（原因未特定） |

タイムライン（`logs/tl_g_ot_5_1.*`）では 1 トークンが「RX 12.5 ms（21 層）→ WX 6.1 ms（3 層）→ RX 2.5 ms（出力）」の 3 区間になり、境界が 1 つ増えても WX の区間が 10.9→6.1 ms に縮み、周期は約 21.8 ms（shim 有り）になる。**ただし RX の VRAM が満杯になる**: VRAM 使用量は RX 3953→4046 MiB（上限 4080 MiB）、GTT（ホストメモリ）が 62→313 MiB に増える（`logs/vram_base.json`、`logs/vram_ot.json`）。この溢れで pp や大きな ubatch の計算バッファがホストに置かれ、pp が 1/4 に落ち、tg も不安定になる。tg だけを使う用途で、RX の VRAM に余裕を作れる場合（例: 別途 KV やコンテキストを小さくする、出力テンソルを小さい量子化にする）にだけ有効（その余裕を作る方法は未検証）。

## 逆順（WX を先頭）の構成

`-dev Vulkan1/Vulkan0 -ts 1/5` は tg 33.56 t/s で C1 より悪い。出力層が RX に移る（`-ot` と同様）が、WX が先頭で dense の 2 層を含む 5 層（perf logger で 7.9 ms）を持ち、RX の区間が実測で約 20 ms（perf logger の演算合計は 13.9 ms）と膨らむ。この RX の約 6 ms 超過は**未特定**（`logs/pl_rv_1_5.*`、`logs/tl_g_rv_*`）。

## tg を上げる具体策と期待幅

## 未検証・限界

- RX 区間が層数にほぼ依存しない点（17〜21 層で 10.3〜10.9 ms）と、逆順構成の RX の超過（約 6 ms）は原因未特定。GPU クロック / 電源状態（RX は sclk 状態 1 の 1.6〜1.7 GHz で最大 2.32 GHz ではない）が関係する可能性はあるが、sysfs の電力設定は変更していない（sudo 不可）。
- perf logger は 1 行パッチ版 `.so` による値（ロガー有効時は演算ごとに同期するので合計が 10 % ほど大きい）。パッチは `~/moe-ep/c1p/patched/ggml-vulkan.cpp`（`GGML_ASSERT` の直前に `ggml_vk_synchronize` を入れるだけ）で、本体ソースツリーは未変更。
- SIGPROF サンプラの実効間隔は 4 ms（HZ=250）。割合は信頼できるが ms 換算は「割合 × トークンあたり CPU 時間」の推定。
- FORCE_MMVQ の数値影響と、`-ot` を使った時の出力のずれ（RX/WX で別のシェーダを使うため丸め差はありうる）は測っていない。
- 温度はすべて 85 ℃未満（開始時 36〜43 ℃、終了時 49〜55 ℃）。測定は `~/bench/gpu-bench.lock` の下で 1 本ずつ。
- C1 の他の掃引（`-ub` 64〜1024）は baseline README の値を使用し、今回は再測定していない（`-ub` が tg に効かないことは `-ub 128`/`512` の基準比較 44.78 / 44.08 でのみ再確認）。

## 自作ツール（`scripts/`）

- `sampler.py`: 子プロセスを起動し、`wait4` の rusage、スレッド別 schedstat、`gpu_busy_percent`・DPM 状態・VRAM 使用量をサンプリング。
- `vkshim.c`: LD_PRELOAD。`vkGetInstanceProcAddr` / `vkGetDeviceProcAddr` を奪って Vulkan 関数の呼び出し時間とイベント（submit、待ち、フェンス成功時刻）を記録。引数は転送のみ。
- `sprof.c`、`sprof_an.py`: LD_PRELOAD の CPU 時間サンプラと集計（`nm` でシンボル解決）。
- `an_phase2.py`、`an_pl.py`、`an_dense.py`、`an_cpu.py`、`an_ts.py`: 集計。
- `go.sh`（ロック + 温度待ち + サンプラ）、`b.sh`、`b2.sh`、`q*.sh`（実行キュー）、`env.sh`。
- tb250 側の作業場所: `~/moe-ep/c1p/`（`bin-patched/` はパッチ版 `libggml-vulkan.so` を含む bin のコピー）。
