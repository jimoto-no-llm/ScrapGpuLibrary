# C1 tg128 が 44 / 52 t/s の2状態に分かれる件（tb250、perf high）

2026-10-21、tb250。ビルド・コマンド・環境は同一（`~/moe-ep/sglx/bench.sh`、PROFILE=0、`-ts 5/1`、`-dev Vulkan0/Vulkan1`）。コード変更なし。

## 結論

| | 52 状態 | 44 状態 |
|---|---|---|
| C1 tg128 | 51.8 | 44.0 |
| 負荷中の RX 6400 gfx クロック（gpu_metrics `current_gfxclk`） | 2320 MHz 固定 | 500〜1700 MHz で負荷に追従して上下（`perf=high` なのに auto の挙動） |
| RX 6400 の負荷中消費電力 | 約 18〜19 W | 約 14 W |
| WX 2100 のクロック | 1219 MHz（sclk 7） | 同じ |
| mclk / socclk / PCIe | RX mclk 1000 MHz、socclk 1200 MHz、リンク同じ | 同じ |
| スロットル（`throttle_status`、`indep_throttle_status`） | 0 | 0 |

状態の正体は RX 6400 の gfx クロックが perf high で固定されているか、されていないか。`power_dpm_force_performance_level` は両状態とも `high` と表示するので、この値では区別できない。

- 実測: クロックの違い（下のセクション「クロック」）。tg と pg の違い。状態が数分から数時間続くこと。
- 未確認: なぜ 44 になるのか（SMU・ドライバ内の原因）。引き金は特定できていない（下の「再現手順」）。
- 推定: RX の gfx クロックが 2320 → 約 1700 MHz 以下に下がると、RX 側の層区間が延びて tg が 15% 下がる。クロック比（0.73）より tg 比（0.85）が小さいのは、tg が GPU 律速と CPU・転送律速の混合であるため。この分解は未計測。

先行調査の「RX のクロック」（perf auto で RX の sclk が 500 MHz に張り付く）と同じ種類の現象。44 状態は perf high のつもりで測っても RX が auto と同様に振る舞う状態であり、perf auto の C1 が 44.0〜44.2 になるのと整合する。ただし 52 状態の最中に perf auto で C1 を測っていないので、auto が常に 44 かどうかは未確認。

## 数値（同一コマンド、REPS=10、PROFILE=0、perf high、C1 と SGLX C を交互）

SGLX C は `GGML_SGLX_SPLIT=Vulkan0:0.5,Vulkan1:0.2,CL11_0:0.2,CL11_1:0.1`。単位 t/s、平均。

pp512 は両状態でほぼ同じ（約 655〜667）。pp は RX の gfx クロックにほとんど左右されない（負荷が高く、固定でなくても max クロックに上がる）。

## クロック（実測）

`sampler.py`（20 ms または 100 ms、1 s）と `gpu_metrics`（v1_3、120 byte）を測定中に記録した。サンプル数が少ないので傾向の確認として読むこと。

`exp17.sh` の 1 セッション目（44、tg 44.1）と 2 セッション目（52、tg 51.6）、SAMPLE_MS=100、`act_gfx>=50` のサンプル:

| | 44 状態 (`cs_e17_s1_1/2`) | 52 状態 (`cs_e17_s2_1/2`) |
|---|---|---|
| current_gfxclk 平均 / 最小 / 最大 MHz | 1456, 1493 / 500, 970 / 2320 | 2320 / 2320 / 2320 |
| average_gfxclk 平均 MHz | 1015, 965 | 1683, 1617 |
| average_socket_power 平均 W | 14, 14 | 18, 19 |
| throttle_status | 0 | 0 |

時系列（tg 区間、100 ms 間隔、`current_gfxclk/act_gfx`）: 44 では `610/24 1090/28 500/56 1135/17 785/25 1035/46 1470/31 ...`、52 では全サンプル 2320。

20 ms サンプラでの `rx_busy>=50` 時の `pp_dpm_sclk`: 52 状態は 100% が `1:2320Mhz`。44 状態（`cs_e16_s3_samp20`）は `1:1695Mhz`（31）、`1:1685Mhz`（14）、1065〜1145 MHz 台などに分散。

WX 2100（Polaris）は両状態とも sclk 7（1219 MHz）で、差はない。

その他の差: アイドル時の RX fclk は 44 状態の 20 ms サンプルで 1193 MHz が 73%、52 状態で 1351 MHz が 89%（`agg.py`）。

pp_features: perf high を書くと DPM_GFXCLK、DS_GFXCLK、GFX_ULV、GFXOFF、GFX_SS が disabled になる。44 状態では負荷が掛かると 15 s 後の読みで enabled に戻っているセッションが多い（`logs/snap_e18_*_1afterhigh` / `_2mid`）。ただし 52 状態でも `exp19` D1 の +23 s で enabled になっており、読み取りタイミングに依存するため、これだけで状態を判別することはできない。

## 状態の挙動（実測）

- 状態はプロセスをまたいで続く。同じ状態が数分から数時間（52: 例 17:36〜18:12 の 36 分、44: 例 22:21〜22:58 の 37 分以上）、perf auto/high の書き直しや、60 s 程度のアイドルを挟んでも続く。1 プロセス内（6 分、`exp20.sh`、tg 120 回）では 52 のまま変わらなかった。
- 切り替わりは稀で、観測した限りでは 1 回の perf 書き直しあたり数 % 程度。例: `exp22` で probe7（23:26:56、52）→ probe8（23:28:12、44）、`exp6` で同一セッション内の run1（52）→ run2（44）。
- 切り替わりの引き金は特定できていない。

## 再現手順

52 状態、44 状態を意図的に作る手順は見つからなかった。次の要因は状態を変えなかった（実測）:

- perf auto → high の書き直し（`exp12`: 10 セッション連続 52、`exp13`: 14 セッション 52、`exp14`: 14 セッション 52、`exp18`: 32 セッション以上 44）
- 書き込み前のアイドル時間 5〜120 s（`exp18`）
- 直前に SGLX C を走らせる、nvidia-smi を5回呼ぶ、他のモデルを読み込む、120 s アイドル（`exp15`、44 のまま）
- sysfs サンプラの有無（20 ms、100 ms、300 ms、1 s。44 状態で tg は 44 のまま、`exp16`）
- 1 本のビジーループによる CPU 競合（`exp4`、45.4。2 本では 36.1 に落ちる）
- 起動時の perf 順序や書き込みを 2 回にすること（`exp19` A/B。ただし run 間で状態が変わる交絡あり）

したがって「測定を揃える」運用手順:

1. perf high を書いてから、短いプローブ（`bench.sh TAG "" -p 0 -n 128`、REPS=2、約 20 s）で C1 tg を測る。47 以上なら 52 状態、未満なら 44 状態。
2. 比較したい状態になるまで、perf auto → 45 s 待機 → perf high → プローブを繰り返す（`exp22.sh`）。52 → 44 の切り替わりは 7 回目のプローブ（約 8 分）で、44 → 52 は `exp17` で 1 回の再試行で観測した。確率的で、所要時間は不定。
3. 状態が目的のものだったら、同じセッション内で C1 と SGLX C を交互に測る（`exp21.sh`、`exp22.sh`）。測定の前後でもプローブして、状態が変わっていないことを確認する。

注意: 20 ms のサンプラは CPU を使うため、52 状態で tg が 52 → 50 に下がる（`cs_e1_*`、`cs_e5_*`、`cs_e7_*`、50.0〜50.2）。100 ms でも同じ。1 s なら影響なし（`exp14`）。性能の測定値はサンプラ無しの run を使うこと。

## 結果が影響を受けた先行測定

- `~/moe-ep/perf/`（10:4x）の C1 high 44.0 と auto 44.2: 44 状態で測定。perf high の効果がなかったのではなく、perf high が効かない状態だった可能性が高い。
- `ph_*`（16:04〜16:11）: 52 状態。`ph2_*`（16:11〜）: 44 状態。2 つの run の差はこの状態の差で説明できる。コード・設定・VRAM 配置・警告の違いではない（`ph_c1` と `ph2_high_c1_1/2` のログのヘッダ・stderr（デバイス情報・警告）は、時刻と温度を除いて同一）。

## ログ・スクリプト

`logs/`:

- `cs_*.csv`: サンプラの出力（20 ms / 100 ms / 1 s。列は `sampler.py` 冒頭）。`cs_*.out` が llama-bench の jsonl、`cs_*.log` が run.sh のヘッダ・stderr。
- `snap_e18_*`: 状態ごとのドライバ状態のスナップショット（`snap.sh`）。
- `exp*.out`: 各実験スクリプトの標準出力。`e21_*`、`e22_*`: 上の数値の元。
- `cs.perf.log`: perf 切り替えのログ（全 auto で終了）。

スクリプト（tb250 の `~/moe-ep/sglx/` にコピー済み。実行は `run.sh` 経由で flock と温度待ちを使い、perf は trap EXIT で auto に戻す）:

- `sampler.py`: 20 ms 間隔（`SAMPLE_MS`）で RX 6400 と WX 2100 の pp_dpm_sclk/mclk/fclk/socclk/pcie、リンク速度・幅、gpu_busy、mem_busy、温度、power1_average、freq1、VRAM・GTT 使用量、CPU 周波数、RX の gpu_metrics を記録する。`SAMPLE_COLS` で列を絞れる。
- `probe.sh`、`exp1..22.sh`、`snap.sh`、`runstat.py`: 実験ごとの手順（各ファイルの先頭コメント）。
- `summarize.py`、`agg.py`: CSV の集計。

実験の一覧（要点）: exp1/2/5/7 = サンプラ付き（52 状態で 50）、exp3 = サンプラの影響、exp4 = CPU 競合、exp6/9/10/11/12/13 = サンプラ無しの連続測定、exp8 = 列グループ別のサンプラ影響、exp14 = 1 s サンプラ（52）と 44 の取得、exp15 = 引き金の探索（成果なし）、exp16 = 44 でのサンプラ影響確認、exp17 = gpu_metrics の取得、exp18 = スナップショットと待機時間、exp19 = perf 書き込みの順序、exp20 = 1 プロセスの時系列、exp21/22 = 最終の数値。

exp11 の mmap 無し側は `-mmp 0`、`--mmap 0` とも llama-bench が "invalid parameter" で終了（rc=1）し、mmap の有無の比較は成立していない（無効な実験。mmap 側の run は通常どおり 44 / 52 を示した）。

## 未検証

- 状態が切り替わる原因（amdgpu ドライバ、SMU ファームウェア、runtime PM のどれか）。カーネルの dmesg と debugfs は権限が無く読めない。
- 52 状態のときの perf auto での C1。
- gfx クロックを固定したときの tg への寄与（RX の層区間の実測分解）。
- ノード外からの要因（電源、温度、他のホスト）。
