# HOT_EXPERT_CACHE 最初の1日の判定（H1 / H2 / H3 / MB-H1 / MB-H2）

測定 2026-10-23、tb250（Celeron G3930 2C、RX 6400 / WX 2100）、llama.cpp `23b0202` の共有ビルド（読み取りのみ）、`Qwen3-30B-A3B-Q4_0.gguf`。
**【実測】** は `logs/` と `trace/` にある値、**【シミュレーション】** は実測トレースを設計書 6.1 のコストモデルに通した値（実機の tg ではない）。`GGML_SGLX*`・SGLX0 の実装はまだ無く、E2E の tg は未測定。
各 run は `~/bench/gpu-bench.lock` の flock + 温度待ち（`adapters/ggml/tools/hec_run.sh`）で1本ずつ。perf は触らず run 先頭に記録（大半 manual、`cpu1_default_t2_a` と `*_t1` は auto。CPU のみの測定なので影響しない）。

## 結論（先に）

**判定: 進む（ただし設計書の前提を4点修正してから）。** 設計書 9 章の基準（tg 7.70 の 1.3 倍 = 10.0 超で進む）に対し、乱数トークンのシミュレーションは実測で補正したモデルでも **約 16〜17**、最悪の仮定（Q4_1 の層を GPU に置けない）でも **約 12.3**、配置が別領域で古いままの最悪ケースでも約 9〜10 で、中止条件（8.5 以下）には入らない。ただし実機の SGLX0 経路の実測が無いので、段階 1〜3 で実測の係数に差し替えて再判定する。

修正すべき前提:

1. **乱数トークンは一様ではなく、自然文より偏る**（設計書 9.1 の「最悪は一様 h≈0.42」は誤り）。llama-bench の合格判定の数字は、自然文より楽観的に出る。実際の文章の速度を必ず別に報告する。
2. **ggml-cpu は既に SSE4.2 でビルドされている**（スカラー経路ではない）。`GGML_SSE42` は `GGML_NATIVE=OFF` でも既定 ON。SSE4.2 で速くなる余地は無く、基準の測り直しは不要。
3. **expert の型が Q4_0 だけではない**: 層 0〜5 の `ffn_down_exps` は Q4_1。CPU では 1 expert が 0.61 ms（Q4_0 の層は 0.276 ms）と 2.2 倍遅く、CUDA/CL11/REMOTE の pdev（Q4_0/Q6_K のみ）では置けない。
4. **CPU と GPU の並列は、2 コアではほぼ効かない**（MB-H2）。GPU の層 1 回あたり約 0.34 ms のホスト側の直列コスト（submit + 同期 + 読み戻し）が CPU 時間に足される。設計書の `max(GPU, CPU)` ではなく `Σ ovh + max(CPU, GPU 計算)` で見積もるべき。

- **乱数**: `llama-bench -p 512 -n 128 -pg 512,128` と同じ手順（`std::rand() % n_vocab`、srand なし、warmup の乱数消費も同じ順）。ソースを読んで合わせたもので、実際の llama-bench の入力トークンとの突き合わせはしていない。pp512 ×2、tg128 ×2、pg512,128 ×2（`trace/bench`）。
- **自然文**（各 先頭512トークンを prefill、その後モデル自身が top-k 40 / temp 0.8 / seed 固定で256トークン生成）: en_doc（llama.cpp の docs）、en_legal（GPL）、py_code（argparse.py）、cpp_code（llama-graph.cpp）、ja_tech（SGL README）、ja_design（この設計書）。

## H3 / MB-H1: CPU の 1 expert（`adapters/ggml/tools/hec_bench.cpp cpu1`）

実重みを GGUF から mmap（層・expert をランダムに選び毎回コールド）。MUL_MAT_ID(gate)+(up)+SWIGLU+MUL_MAT_ID(down)、N=1、n=1..8、ggml-cpu 2 スレッド。`logs/cpu1_*`。

| ビルド | 全 Q4_0 の層(42) 1 expert | 固定 | 帯域 | Q4_1 down の層(0〜5) 1 expert |
| --- | --- | --- | --- | --- |
| 現行（共有ビルド、SSE4.2 ON） | **0.276 ms** (a/b 0.276/0.276) | 28 µs | 9.6 GB/s | 0.61 ms (4.5 GB/s) |
| 現行、1 スレッド | 0.532 ms | 31 µs | 5.0 GB/s | - |
| `GGML_SSE42=OFF`（SSE2 のみ。**スカラー経路**） | 1.43 ms | 60〜100 µs | 1.9 GB/s | 1.38 ms |
| SSE2 のみ、1 スレッド | 2.83 ms | - | - | - |
| 現行 + `GGML_OPENMP=OFF` | 0.276 ms | 24 µs | 9.6 GB/s | 0.61 ms |
| 現行 + `-mtune=skylake` | 0.278 ms | 27 µs | 9.5 GB/s | 0.61 ms |

- **現行ビルドはスカラーではない**: `build.ninja` の全 CPU ファイルに `-msse4.2`、`ggml_vec_dot_q4_0_q8_0` は SSSE3 経路（逆アセンブルで `pmaddubsw` / `psignb`）。設計書 1.2 の「AVX 系全 OFF で SSE42 を明示していない」は、SSE42 が既定 ON であるため当たらない。SSE2 のみにすると 5.2 倍遅い（これが「スカラー」の値）。
- **SSE4.2 で速くなる余地は無い**（既に使用中）。OpenMP OFF・`-mtune` も差なし。したがって **30B / LFM の基準（CPU を含む -ncmoe 系）の測り直しは不要**（基準が上がる可能性は今回の変種では見つからなかった）。実施していない。
- CPU の t_cpu: 設計書の 0.35 ms に対し、Q4_0 の 42 層は 0.276 ms（約 21% 速い）、層 0〜5 は 0.61 ms。48 層の加重平均は 0.32 ms。2 スレッドは 1 スレッドの 1.93 倍で、メモリ帯域ではなく計算律速に近い。
- Q4_1 の層 0〜5 は全 expert CPU のとき 1 層 4.9 ms（Q4_0 層の 2.2 ms の 2.2 倍）、6 層で約 16 ms/トークン余計にかかる。CPU のみの基準 tg 3.10 にも約 5% 含まれている。

## MB-H2: CPU と GPU の同時実行（`hec_bench.cpp conc` / `spin`）

RX 6400 の slot 配列（24 slot、Q4_0）で m_gpu expert、CPU(mmap) で n_cpu expert（m+n=8）。x/ids 書き込み → GPU submit(async) → CPU → sync → 読み戻し、の設計 3.2 の流れ。`logs/conc_*`, `logs/spin_*`。

| m_gpu:n_cpu | GPU 単独 | CPU 単独 | 同一スレッド async の壁時計 | 壁時計 / (GPU+CPU) | 壁時計 / max | CPU 部の遅れ |
| --- | --- | --- | --- | --- | --- | --- |
| 6:2 | 301 µs | 585 | 947 | 1.07 | 1.62 | 1.03 |
| 4:4 | 248 | 1232 | 1493 | 1.01 | 1.21 | 0.94〜1.03 |
| 2:6 | 230 | 1687 | 2073 | 1.08 | 1.23 | 1.01 |
| 7:1 | 336 | 309 | 526 | 0.81 | 1.56 | 1.08 |

（CPU 2 スレッド、`conc_vk0_t2_a`。`_b`、1 スレッドも同傾向。）

- **並列にならない**: 同一スレッド async では壁時計 ≈ GPU 単独 + CPU 単独（0.81〜1.08）。GPU 側の追加は CPU 部の後ろに **約 0.34 ms/層**（submit 約 0.1 ms + 同期と読み戻し約 0.23 ms、n_cpu ≥ 2 のとき一定）。
- 原因は GPU が進まないことではない: ホストを純粋に待たせる `spin` では、D ≥ 200 µs で残りの待ちは約 8 µs（GPU 計算は完全に隠れる。ALU でもメモリ走査でも、他に1スレッド回していても同じ。3 本目のスレッドが入ると崩れる）。RX の 1 層の「GPU 単独」250〜370 µs のうち、GPU の計算は約 70〜100 µs で、残りは submit・同期・読み戻しのホスト側の直列コスト。
- **ワーカースレッド方式は悪い**: CPU 2 スレッド + GPU ワーカーで 3 本が 2 コアを取り合い、CPU 部が 1.12〜1.65 倍遅く、壁時計/和は 1.0〜1.7。CPU 1 スレッド + ワーカーを core 1 に固定(`conc_vk0_t1_pin`)すると CPU 部の遅れは 1.01〜1.03 に収まるが、壁時計は同一スレッドと同等（4:4 で 2570 対 2526 µs）で、得は無い。ggml-cpu の `--poll 0` でも差なし。
- **GPU の待ちは CPU を圧迫しない**: ggml-vulkan の同期は `waitForFences`（ブロッキング）で、同一スレッド方式の CPU 部の遅れは 1.00〜1.08。CPU は 2 スレッド全部をコールド計算に使える。
- WX 2100（Vulkan1）も同様（`conc_vk1_t2`: 8 expert の GPU 単独 1058 µs、4:4 の壁時計 1590 µs vs CPU 単独 1130 µs）。GT 730（CUDA）と GT 430 は ggml 側に無く未測定。
- 結論: 設計 6.1 の `max(G, C)` は楽観的。**層の時間 ≈ CPU 時間 + 0.34 ms × 使った GPU の数**（GPU の計算は CPU の後ろでなく隠せるが、ホスト直列コストが残る）として見積もる（上の「補正後」の表）。GPU が RX 1枚でも 48 層で約 16 ms/トークン（tg 25 → 16〜17 に低下）。層ごとに GPU を呼ぶ回数を減らす（hit の無い層は呼ばない、RX の submit を 1 層に 1 回に固定）、グラフ構築の省略（plan キャッシュ）が効く。

## 設計書の判定

`T_pred` の基準 `1000/T_pred > 7.70 × 1.3`（乱数トークン）を、補正後のモデル（実測の t_cpu・MB-H2 のホスト直列）で評価: 乱数 **16.2〜16.9**（構成 C、静的 prefill/oracle）、構成 A でも 15.2〜15.8。Q4_1 の層を GPU に置けない場合 12.3〜12.5。いずれも 10.0 超 → **進む**。自然文の見積もりは 13〜15（prefill 由来の配置）で、基準(7.70)の約 1.8 倍。別領域のままの古い配置 8.9〜12.5 は、配置し直しが働かないと 1.1 倍（8.5）付近まで落ちる。

進める前に直すこと:
1. 設計書の 9.1「乱数は一様」、1.2「SSE42 を明示していない」、1.1「全 expert が Q4_0」を、上の実測で差し替える。
2. 層 0〜5 の Q4_1 down: RX/WX(Vulkan) に Q4_1 のスロット配列を持つか、CPU のままにして 12.3 前後を覚悟するか、段階 0 で決める（down のみの再量子化は数値が変わるので KLD 基準の再確認が要る）。
3. 6.1 のコストモデルを `ovh + max(...)` 型にし、GPU 呼び出し回数を設計の主要な変数にする。GT 430 / WX の固定費も同様に再測定。
4. 配置は **同じプロンプトの prefill の統計**から作り（static-prefill）、LRU 型の都度入れ替えは避ける。ヒステリシスは「ほぼ静的」で十分。

## 未測定・限界

- トレースは CPU 実行（fp32 の丸めが GPU と異なる）。層 47 の prefill は未観測。乱数トークンが llama-bench の実トークンと一致することは、ソースの読み合わせのみで未検証。
- E2E の tg/pp は未測定（SGLX0 の MoE 経路が未実装）。pp の見積もりは流し込み律速の単純式。
- LFM の測り直しは、SSE4.2 が既に ON のため行っていない。MB-H3〜H6（境界 48 層、upload 中の計算、prefill 流し込み、GT 430 の job）は今回の範囲外。GT 730（CUDA）/ GT 430 の MB-H2 は未測定。
- llama.cpp `23b0202` には実験的な `llama_context_params.moe_cache_size`（`src/llama-moe-cache.cpp`、ホストの expert を LRU でデバイスにキャッシュ、hit rate をログ）が既にある。本設計との重なり・比較は未調査（次に見る価値あり）。

## 再現

`scripts/queue*.sh` が実行したコマンド列（`build_variant.sh` は ggml-cpu のみの変種ビルド）。トレース: `hec_trace -m … --cpu-lib … --out trace/X --bench 512,128,512:128 --reps 2` / `--text F --n-prompt 512 --n-gen 256 --seed 1234`。シミュレータ: `python3 tools/hec/sim.py --trace trace/bench --trace trace/en_doc … --out sim_design.json [--cpu measured --serial-host 0.34 [--q41 none]]`、表は `tools/hec/make_tables.py`。
